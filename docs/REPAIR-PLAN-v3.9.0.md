## 1. 总体决策

**不再整仓从零重写。保留已经有测试支撑的纯判定、目标模型、解析器及客户端包验证；重构状态协调、系统动作、恢复和更新信任边界。**

分成两条明确的路线：

- **R：现有产品可靠性修复，属于本次完整修复主线。** 解决所有已确认缺陷、不实状态、恢复漏洞、更新风险、测试失效和文档漂移。达到“在明确范围内可靠执行、能核验、失败可恢复”的标准。
- **S：连接级强约束，单独决策和验收。** 如果产品必须在守护器未检测到异常前也阻止应用直连，需要独立的系统层执行能力与受控出站路径。不是 R 完成后自动获得的能力，也不能用“零泄露”笼统命名。

保留 Tauri 2、纯静态前端、无前端构建步骤、现有方向 A 界面、安装器 AppId、现有通知及客户端更新功能。前端测试可使用开发依赖，不给应用增加 Node.js 运行依赖。新增依赖逐项论证，不为重构引入大框架。

### 1.1 完成定义

R 主线完成必须同时满足：

1. 本文覆盖矩阵中的每项已修复并有对应回归证据，不能只以现有测试数量全绿结项。
2. 系统动作有结构化结果和后置核验；未知、部分失败、不支持绝不显示成成功。
3. 更新、卸载、退出、恢复、暂停、首启、崩溃重启有一致且可解释的状态契约。
4. Windows 原生防护与生命周期验收完成；macOS 按所宣称的平台和架构分别验收。未具备环境的部分明确保持“未验证”，不能宣称全平台已完成。
5. 文档、界面和实际能力一致；没有将锚点通过、规则存在等同于应用全部流量安全。

不得以“完整修复”为由，偷偷把现有“不知道出口时不自动杀进程”的语义改成另一种产品策略。

## 2. 需要批准的行为变化

以下给出推荐方案。批准规划时确认这些行为；实施前不得按已经生效处理。

| 决策 | 推荐方案 | 兼容与边界 |
|---|---|---|
| D1 默认隔离范围 | 新安装默认隔离受管应用，不默认全机断网 | 旧配置先保留、备份并展示迁移差异，不静默改档位。缺少可靠恢复执行器的全局断网/禁网卡能力不可继续自动触发，必须明确提示能力受限并引导选择 |
| D2 全局断网保留方式 | 保留为高级应急能力；只有独立恢复能力就绪才允许新增动作 | 不再承诺联网探测可以无条件自动解开全局断网；恢复网络与解除应用隔离分开 |
| D3 暂停、解除和退出 | 暂停停止新的自动杀进程、残留清理、升级及升级式断网，保留已有保护；显式解除是另一操作 | 同范围规则的维持/修复是否继续须在文案中写清，推荐继续维护既有隔离。手动操作仍需明确请求。正常“恢复并退出”表示停止保护并恢复本产品改动，失败不假装退出成功 |
| D4 信息不足 | 默认保留 Unverified 不触发新的自动杀进程，但禁止从守护器启动，也不得据此自动解除隔离 | 严格模式中“信息不足是否立即隔离”另行选择；不能将新策略伪装成普通 bugfix |
| D5 守护器外发策略 | 探测、更新、通知统一经过可审计策略；默认禁止静默直连回退 | 有代理但无法证明是应用同路时仍标证据不足。通知正文默认脱敏；旧通知可能包含敏感信息的行为需迁移提示 |
| D6 首次可信更新 | 通过独立可核验的迁移渠道引入信任根，后续强制验签 | 当前未验签旧版本不能认证“第一跳”。没有可信安装器/带外核验条件时保留检查提醒，暂停自动应用 |
| D7 权限与恢复执行器 | 最终普通权限 UI + 不加载 WebView 的窄接口高权限执行器 | 优先同一签名二进制的不同进程角色；服务或计划任务的安装、启动和卸载须单独授权，不能偷偷常驻 |
| D8 强直连约束 | R 先完成，S 单独进行可行性验证 | 如果用户要求本轮即具备连接级约束，S 必须成为发布阻断项，而非宣传中提前兑现 |

正常退出恢复网络、强退后继续隔离、强退后自动恢复网络，是不同故障策略。**没有独立执行体时，进程被强杀不可能执行退出代码；保持阻断和自动开网也不能同时无条件保证。** 新契约必须取代这类相互矛盾的承诺。

## 3. 统一模型与不可违反的规则

### 3.1 将四种信息分开

建议新增或调整的数据模型，具体命名在实施时确定：

```text
PolicyVerdict       = Pass | Fail | Unverified
AccessEvidence      = 代理解析、路由线索、观测范围、时间、修订号
ProtectionIntent    = 原因集合、受管对象、所需动作、配置/运行代次
ProtectionObserved  = 实际规则、有效策略、对象清单、网卡状态、核验时间
OperationStatus     = Verified | Partial | Failed | Unknown | Unsupported | NotApplicable
OperationReceipt    = 操作ID、资源级结果、错误、核验范围、剩余恢复事项
```

`Verified` 只能表示具体后置条件在明确范围内已核验。例如“规则和有效策略已核对”不是“所有现有连接、回环代发与 UDP 均已阻断”。界面必须展示核验范围，不能由规则条数推导无限范围的保护。

- 手动封锁、未接入兜底、出口异常隔离分别拥有原因标记。一个原因解除，不能顺带撤掉其他原因仍需要的规则。
- 无守护对象、目标未安装、解析不到程序、全部目标停用，均不得变成“所有应用已保护”。
- 查询失败不是“没有规则”；没有规则不是“清理调用失败”；平台不支持不是“已成功执行”。
- 规则发现被删除、程序升级、有效策略变化、新网卡出现，都使已有核验失效并触发重新核对。

### 3.2 生命周期与保护状态正交

生命周期建议为：`Unconfigured / Disarmed / Armed / Maintenance / Stopping`。
保护状态建议为：`Pending / Monitoring / Isolating / Quarantined / GlobalCut / Recovering / NetworkReadyAppHeld / Degraded`。
暂停作为独立状态，而不是用一个“暂停”值覆盖当前是否隔离。所有合法组合及拒绝的组合写入状态机测试。

- 首次未配置：可进行经允许路径的非破坏性检测，禁止启动，不自动结束应用或断网。
- 已布防后配置错误：保持旧的有效配置和现有保护，拒绝错误保存；不能因坏配置自动转为无保护。
- 升级发现旧恢复记录：优先处理 `RecoveryPending`，不能当作首启并清掉现场。
- 暂停确认返回之后，不得再开始新的自动 kill；已发出的命令若无法确认取消，状态应为 Unknown 并核对，不能谎报取消成功。
- 自动恢复应用隔离，仅在当前配置/运行代次的必要目标全部 Pass、访问证据满足选定策略、系统状态核验完整时进行。信息不足不解除。

### 3.3 单一协调器，而不只是多加几把锁

新增一个权威命令协调器，接受定时检查、手动检查、Launch、配置更新、暂停、恢复、清理、更新、退出和卸载请求。

- 探测可有界并行；状态提交与系统副作用串行协调。
- 每轮捕获 `config_revision + runtime_epoch + operation_id`。配置、暂停、恢复、退出或维护切换使旧任务失效；旧结果不得更新新状态或触发旧策略。
- Launch 排队或等待当前代次的有效检查，不得因“已有检查”返回默认通过。真正启动前重新验证代次、布防及隔离状态。
- 超时命令不代表没有执行：保存 Unknown，后置核对后才能做相反动作。
- 所有慢 I/O 在状态锁外完成；StateView 只读取不可变快照，不扫描进程或执行命令。
- **跨进程执行权必需**：急救 CLI、旧实例、新实例、安装器和多个用户会话必须协调机器级资源。单实例 GUI 插件不能替代系统动作所有权。
- 机器级锁/租约有受控权限、持有者身份、代次与交接记录；不能通过一个可伪造的锁文件取得特权。全局网络资源独占，用户级受管范围需隔离。

## 5. 具体修复设计

### 5.1 防火墙与接入路径：R01、R03、R05

1. Windows 查询采用结构化 API 或受限的结构化 PowerShell 输出；核对防火墙服务、有效配置文件、规则是否启用、策略是否允许本地规则合并、程序/方向/地址族等。返回码、规则条数仅作辅助信息。
2. 规则使用本产品可识别的唯一资源 ID 与分组，记录安装实例和作用域。导入旧规则时同时核对已知名称与目标路径，不用通配符删其他应用规则。
3. 新覆盖先添加并核验，旧覆盖最后撤销；禁止“为了确认仍生效先删再加”。失败可重试，采用限频退避及健康核对，避免每轮重复创建。
4. 防火墙关闭时提示布防前置条件并按已批准策略处理；开启不等于“不影响流量”，不得改用户默认出站策略或覆盖组织策略。正常解除不顺便关闭系统防火墙。
5. 代理解析覆盖单项、多协议、大小写、空白、IPv6、端口范围、缺失地址和非法形式；禁止凭地址缺失就回退一个无关配置端口并说成应用同路。
6. PAC/WPAD、绕过表、不同进程代理设置须产生明确证据等级。不能完整解析/验证的情况显示 Unknown；不猜测、不为了确认出口自动走物理网络探测。
7. TUN 名称仅作候选，修正 UTF-16 长度、空指针和错误分支；核对接口状态及目标相关路由，分开 IPv4/IPv6。即便有路由证据，也不升级成“应用所有流量已强制代理”。
8. 防护目标清单取已注册包身份、当前运行映像、安装清单及升级中的受管路径；不再单靠最高目录名。新版本先纳入覆盖再撤旧版。原生 CLI 单列；共享 Node/Python 宿主不得整体封禁。

### 5.2 进程观察与清理：R04、R05、R16

- 一个 ProcessWatch 服务维护快照，GUI、状态推送、残留监测和防火墙路径发现共用。缓存带时间和失效标记。
- 进程身份至少包含 PID、创建时间、规范映像、父身份和所属会话；终止前重新核对身份，避免 PID 复用。
- 区分桌面根进程、renderer/GPU/crashpad、CLI 根及已确认后代。记录退出前关系，不能在父进程消失后只凭现有 PPID 猜归属。
- 根进程退出后进入既定宽限期，快速重启/自动更新可取消清理；到期处理已确认残留并再扫。权限拒绝、未退出、再生成均在报告中列明，不把一次 kill 调用当成清空。
- 活终端中的独立 CLI 默认不被“桌面退出清理”波及；显式一键清理和熔断按已批准的 Claude CLI 语义执行。不要擅自扩大其他 CLI 产品的结束范围。
- 若进程被重新托管或在观察前已孤儿化且无法证明归属，报告未确认，不杀所有同名进程。受管启动可评估 Job Object，但需验证应用兼容，不能假设能够接管所有外部启动。

### 5.3 恢复是持久事务：R02、R06、R10

**写前账本**：任何规则变更或禁用网卡前，先持久化事务 ID、运行代次、资源所有权、原状态与计划。每步完成后记执行结果和后置核验。原始基线不能被重试覆盖。

- 网卡使用稳定 GUID 等身份，名称仅展示；只恢复本产品确实改变的网卡，不“启用所有网卡”。
- 文件写入、刷新、原子提交和故障重放分别测试；不能假定 rename 单独保证断电持久性。
- 账本读取区分 NotFound、损坏、权限拒绝和 I/O 失败。损坏保留证据，进入 RecoveryPending；不删账本、不盲目撤最后一道保护。
- 特权账本置于受控权限位置；用户可写的 JSON 不得作为高权限任意操作指令。迁移旧账本时验证已知规则及资源，无法证明的交由明确恢复流程。

**两种恢复请求不得混淆：**

A. 安全恢复业务网络：暂停新的副作用 → 核对隔离范围 → 保留全局 Block 恢复本产品禁用的网卡 → 核验 → 满足预先定义的安全条件后撤全局 Block → 系统网络恢复但应用继续隔离 → 当前代次重新验证 → 满足策略后解除相应应用隔离。

B. 停止保护并恢复网络：用户明确接受停止保护，协调器停止重新施加规则 → 恢复本产品改动、解除相应规则并核验 → 标为未布防，不冒充“出口已安全”。这是急救和完整卸载所需的离线路径，不能依赖外部探测成功才能执行。

**A 的重要限制**：应用路径 Block 不一定挡住回环代理代发、已建立连接或代理内排队数据。不能仅凭规则存在或进程已退出就自动恢复全局网络。无法证明隔离条件时停止 A，提供 B 的明确选择；不得后台临时开网“试一下”。也不得擅自杀共享代理以求通过验收。

**独立恢复能力**：新增全局断网/禁网卡前，要求经过验证的脱离 UI 生命周期的恢复执行器和离线入口。强退、重启后由该执行体重建状态；它不能仅凭缺少主进程就无条件开网。故障时优先保持何种隔离、何时允许恢复，属于 D2 的明确策略。未实现该能力的版本不得启用相应新增高风险动作。

### 5.4 所有退出入口走同一协议：R06、R09、R13

| 入口 | 必须执行的协议 |
|---|---|
| 关闭窗口到托盘 | 仅改变可见性，不撤销保护 |
| 正常恢复并退出 | 取得执行权、停止新任务、执行 B、核验成功后退出；失败保留可操作界面/恢复执行器 |
| 急救 `--restore` | 无需 GUI/互联网；协调存活实例停止重施规则，完整恢复本产品范围；输出结构化分项结果，失败非零 |
| 旧式 `--uninstall` | 和安装器使用同一恢复契约；恢复失败禁止自删及删除恢复资料 |
| Inno 卸载 | 在可取消的删除前阶段取得恢复成功回执并复核；不能先 taskkill 再期待退出回调清理 |
| 程序更新 | 独立的维护/交接事务，不能借重启偷偷解除隔离，也不能由启动 heal 把保护清掉 |
| 崩溃/断电/强退 | 不依赖进程退出回调；由账本及独立执行体恢复可操作状态，报告实际剩余保护 |

恢复成功是本产品相关动作全部达到请求的后置条件；“未找到本产品资源”可以是幂等完成，但查询失败不能冒充没有资源。更新/退出/卸载同时到达时必须有唯一被接受的所有者。

两种卸载默认保留用户数据；清数据是单独可选操作，且不能提前删除未完成事务和唯一恢复执行器。迁移与回滚中也不能简单还原整个用户目录覆盖正在生效的账本。

### 5.5 可信更新与权限：R09、R15

**近期阻断策略**：处于隔离、全局断网、lockdown、RecoveryPending 或无法确认系统状态时，不应用自身更新；允许安全路径下检查、下载、验签后等待。不要为安装新版本自动解除保护。

**信任链：**

- 使用成熟验签库，复用 macOS 的已验证思路而不手写密码算法。签名清单绑定产品、版本、平台、架构、渠道、制品类型、精确名称、大小、SHA-256、发布序号、更新协议版本。
- Windows 安装器/高权限组件的 Authenticode 发布者验证与清单签名是两层控制。证书、维护者密钥和可信初次分发是实施依赖，不假设现在已具备。
- 清单大小受限；验签后严格解析，拒绝重复/缺失字段及清单与制品不一致。版本解析严格，发布序号/元数据版本防重放，不把非法版本段按零处理。
- 第一次信任根必须独立核验。旧更新器拉到签名新版本并不意味着旧更新器验证了签名；缺少迁移条件时禁自动应用，不能从同一未受信下载位置取公钥再自证。
- 正式私钥不入仓库/日志，测试用临时密钥。定义 key-id、旧根授权新根、过渡双签、离线跨版本升级和撤销流程；根失陷要靠预置恢复信任或独立验证重装。
- 网络防降级与本地故障回滚分开。回滚只能用当前事务保留的上一可信版本；不能回滚信任元数据高水位或撤销记录。

**下载与应用：**

- 流式下载、增量哈希、清单/签名/制品各自硬上限、超时与取消；检查实际读取字节而非只信响应头。
- 管理员专用受控目录、随机名字、独占创建、拒绝重解析点和不安全父目录；受控句柄/文件身份贯穿验证与复制，安装侧再次验证。
- 检查、下载、应用、卸载采用跨进程串行化和状态代次；后台检查不能覆盖正在应用的状态。
- 受信交接者接管事务与保护责任，等待准确旧进程及单实例锁释放，替换并验证新程序，再启动并等待认证的 Ready/接管回执。spawn 成功不算升级成功。
- 每个阶段失败均有回滚或可恢复失败态，保留唯一可启动版本。不能只把 `process::exit` 换成普通退出，因为普通退出当前会撤保护。
- 制品构建完成后先签可执行文件，再计算最终摘要并签清单，最后独立复验整套资产后发布。保持资产命名兼容；现有代码已经排除 setup，不能把这一点重复算新修复。

**权限拆分：**

先加 CSP、禁止任意导航、持续输出转义和明确 IPC schema。随后普通 UI 与窄接口高权限角色分离，可以评估同一二进制用显式提权启动另一角色。

高权限端自行解析受管目标、规则 ID、安装位置及可信候选，认证调用者、会话、协议、授权范围与代次；不接受任意脚本、任意 PID/路径/URL，也不信任 UI 提交的“已验签”。只删除 requireAdministrator 或暴露通用命令执行器都不算完成。便携目录用户可写，不能宣传为与受保护安装目录同等抗本地篡改。

### 5.6 配置、外发和 UI：R08、R11–R14、R17

- `save` 改为 Result；配置校验、持久化、内存提交和修订提升构成一次提交。失败不更新内存、不报已保存，UI 保留待保存输入。
- 加载与迁移保存拆开；只读 `--check` 和状态快照不自动创建、迁移或重写用户文件。配置不可读不偷偷恢复默认并继续布防。
- 所有服务通过 NetworkPolicy 创建传输：显式代理、已批准的系统路径、或禁止请求；严格模式无直连回退。更新允许的重定向源受限，通知凭据不得随重定向发送。
- 发送外部通知前检查允许字段；默认只发目标别名、状态和错误码等脱敏内容。需要包含出口信息时单独授权并预览；绝不含凭据。队列考虑数据最小化、加密与权限，不假定 DPAPI 保护凭据就等于保护全部消息。
- 本地用于诊断的原始网络信息如确有必要，明确存储范围和保留期；分享、截图、导出默认脱敏，不把真实用户数据作为测试夹具。
- 旧队列不未经确认自动发送可能含敏感字段的消息；采用可回退的迁移或待确认状态，不直接删除用户记录。
- UI 将“锚点通过／规则已核验／覆盖不足／恢复未完成”分开，保留错误直到用户关闭或真实故障解除。支持进行中、失败、重试、不支持及未布防状态。
- 手动封锁保持到明确解除或按预先声明的生命周期结束，不被下一次自动检查覆盖。暂停、解除、恢复并退出采用不同文字。
- 反重力等 Reachability 目标显示“可达性通过”，不能表示 IP/地区合格；HTTP 403/404 等只证明请求可达，不证明业务可用。
- 不改皮肤、不加动效。先更新 `guard://state` 测试契约，再验当前页面；修复旧测试、实际 DOM 和类型载荷不一致的问题。

### 5.7 macOS 与功能保留：R07

平台能力从后端统一导出；编译期接口必须完整。macOS 不支持的网络隔离返回 Unsupported，不用返回 true/0 的成功空壳。对于本平台从未创建的网络资源，清理可为 NotApplicable，不能声称替其他产品恢复了网络。

保留进程守护、启动门禁、通知和客户端更新的既有能力与签名校验。Mac 原生验证工具缺失/失败即停止安装，不能跳过校验。历史移植验收属于旧基线，不能替新版本、Intel 真机或最低 macOS 版本背书。

### 5.8 连接级强约束：S 路线

先做隔离环境可行性验证再选实现。Windows Filtering Platform（WFP）或常驻执行器只是候选，不是自动解决一切的答案。

必须明确：受管进程身份、用户绕过启动、IPv4/IPv6、TCP/UDP/QUIC、DNS、既有连接、回环代理、代理自身直连回退、共享代理排队和再转发、休眠恢复、程序升级及系统权限对手边界。

共享代理的外连不天然携带原应用身份，不能把代理进程全部放行后称为应用已限制。必要时要求专用受控出站路径/代理协作；无法满足者标为不支持严格模式。管理员主动关闭规则等对手模型也必须明示。

在数据面实测通过前，只能称“可靠性修复版”，不能称“所有流量零泄露”。

### 7.3 性能预算（拟定验收目标，不是当前实测）

正确性先于优化。统一硬件/数据/场景做修复前后 A/B，分别测主进程和 WebView2，不只宣传主进程占用。

- 状态快照读取零系统扫描；最多一个共享进程观察服务，避免多个扫描器重复刷新。
- 慢 OS 命令不持状态锁；纯状态 IPC 响应 p95 目标 <100ms，慢动作通过异步操作状态返回。
- 已稳定驻留、窗口隐藏、无更新下载时，主进程 10 分钟平均 CPU 目标 <1% 单核等价；达不到先归因，不降低检查质量凑数字。
- 8 小时稳定性：无任务/句柄/线程无界增长；私有内存预热后无持续增长趋势，末段相比稳定基线增长目标 <10% 或给出明确缓存原因。
- 更新下载内存与制品大小解耦；缓冲有固定上限。目标数量和并发有界，慢目标不无限创建线程。
- 冷启动、窗口展示、首查时延分别测；网络时延不和本地 UI 性能混为一谈。

4. 保留安装器 AppId、用户配置/通知/客户端更新状态；飞书凭据保护不回退明文。
5. 旧的断网档位不偷偷改；能力不足时明确阻止新增高风险动作并提示，不把未完成迁移当“正常守护”。
6. 保护中的实例优先完成可信接管/恢复，不把升级后的 `first_run` 当清场许可。

### 8.2 回滚

- 配置回滚、程序回滚、信任元数据和系统保护账本分别处理。不能简单拷旧 exe 并回退整个数据目录。
- 有活动保护/未完成恢复时，先由兼容账本的可信执行器接管，再回滚程序；不让旧版无法理解的新账本变成孤儿断网。
- 更新备份保留到新实例接管、健康核验与事务提交；回滚仍验证签名和版本身份。
- 失败时保留操作回执、受控账本、可执行恢复入口和用户数据；绝不以“重置全部防火墙/删除配置”兜底。

### 8.3 发布

- 纯确定性 bugfix 可整理为 v3.9.x；默认策略、权限流程和 UI 状态有变化的整合版建议 v3.10.0。版本在范围冻结后确定，不提前打 tag。
- 内部批次不等于对外可发布：M1 全绿并不代表 M2/M3 的防护闭环已完成。
- R01–R09 高优先级问题、恢复/更新信任门槛和宣称支持的平台验收未闭合，不作为“完整修复版”发布。
- 准备发行说明时逐项写“修复/能力变化/仍不支持/未验证”，保留准确的产品边界。
- 发版、上传 GitHub、本机静默升级、真实系统验收都要在用户批准后执行；当前规划不授权这些动作。

### 边界声明

M1–M3 全绿只代表"已确认的缺陷项被修复且有回归用例"，**不代表**防护闭环成立：更新验签与可信迁移、统一外发与脱敏、CSP 与权限拆分仍在 M4，性能实测与全量一致性验收在 M5。在 M4/M5 完成前，任何"完整修复"的对外表述都不成立。

M3 已知未覆盖（如实记录，不在本批宣称完成）：
- 流程 A（安全恢复业务网络：先撤全局 Block 再核验）尚未单独实现，目前只有流程 B。
- 断电/强杀场景的账本重放只有单元级验证，未做系统级故障注入（S 类用例需单独授权）。
- 更新交接（`Maintenance` 事务）仍沿用旧路径，属 R09/M4 范围。
- `netcut` 的恢复计划、账本读取已有纯函数单测，但"按 GUID 启用网卡"仍依赖真实 `Enable-NetAdapter`，系统级验证归 M5。

M4 已知未覆盖（如实记录）：
- 更新包只按 GitHub 提供的 sha256 摘要校验，**没有独立签名清单**：能改 GitHub Release 的人也能改摘要，这一层要等维护者密钥与签名流水线（计划 5.5 的"信任链"整段仍未落地）。
- 没有"发布序号/更新协议版本"防重放，也没有旧根授权新根、双签过渡、撤销流程。
- 升级仍走 `process::exit(0)` 直接替换，没有"受信交接者接管事务 + Ready 回执"。
- 权限拆分（普通 UI + 窄接口高权限执行器）未做：程序整体仍是 `requireAdministrator`，CSP 与导航限制只是"减少攻击面"，不等于拆分完成。
- `withGlobalTauri: true` 仍开启：前端零构建、`ui/ipc.js` 依赖 `window.__TAURI__.core.invoke`，关掉会直接失去 IPC；当前靠 CSP（禁内联脚本）与导航限制降低风险。
