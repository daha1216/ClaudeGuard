# Claude / Codex 客户端更新

客户端更新独立于 ClaudeGuard 自身的 GitHub 更新。Claude、Codex 分别有开关、状态、下载目录和后台工作线程，默认关闭。

## 使用方式

在设置中启用对应客户端的自动更新。守护器每周检查一次，也可点击“检查 Claude 更新”或“检查 Codex 更新”立即检查。关闭自动更新时，手动检查只查询版本，不自动下载或安装。该频率仅控制 ClaudeGuard，不修改客户端或 Microsoft Store 自身的更新策略。

发现新版后，在守护检查通过且没有熔断时下载并验证官方包。客户端或相关 CLI 仍在运行则等待正常退出：

| 客户端 | 需要退出的相关程序 | 更新对象 |
| --- | --- | --- |
| Claude | Claude 桌面应用、Claude Code | 当前用户已安装的官方 Claude MSIX 包 |
| Codex | Codex 桌面应用（其进程名可能为 ChatGPT）、Codex CLI | 当前用户已安装的官方 OpenAI.Codex MSIX 包 |

退出窗口不一定等于所有后台进程已退出，界面会显示检测到的等待原因。目前进程检测覆盖原生 `Claude`、`ChatGPT`、`Codex` 和 `codex-command-runner` 进程，不保证识别所有由 `node.exe` 托管的 CLI；更新前请自行确认相关任务已完成并退出。更新器不强制终止应用或 CLI。保持守护器运行，满足条件后才处理；安装过程中，守护器阻止再次启动 Claude。

## 包来源与校验

- Claude 使用 `claude.ai` 官方桌面更新入口，仅接受 `downloads.claude.ai` 固定发布路径中的 HTTPS 包。
- Codex 使用 `persistent.oaistatic.com/codex-app-prod/` 官方稳定版 MSIX，检查响应中的包身份、架构和版本元数据。
- 仅支持已注册的官方包身份 `Claude_pzs8sxrjxfjjc` 或 `OpenAI.Codex_2p2nqsd0c76g0`；不在未安装时新装，不降级，不更新其他发行版。
- 安装前使用 Windows 验证签名，核对包名、发行者和 CPU 架构与现有包一致，并核对包版本与本次目标一致。版本按数字段比较，不能使用字符串排序。
- 下载的分段响应需匹配长度、Content-Range 和 ETag；先保存为 `.part`，完整后再验证。文件缺失、版本变化或校验失败都不会安装残包。

缓存位于守护器可执行文件旁的 `ClaudeUpdates` / `CodexUpdates`，需要可写空间。客户端沿用 Windows 管理的原安装位置和用户档案。守护器不读取、导出或清理客户端 Cookie、令牌或账户数据。

原位升级保留应用数据，但不能保证永远不需要重新登录：官方会话过期、服务端撤销或客户端要求重新认证仍可能发生。

## Windows 已接收不等于更新完成

正常部署使用 Windows PowerShell 5.1 的 `Add-AppxPackage`，附带 `-DeferRegistrationWhenPackagesAreInUse -RetainFilesOnFailure`。Windows 可以先接收包，等待后续完成当前用户注册。此时守护器保存目标版本并显示“等待生效”，不会将安装命令返回成功直接当成升级完成。

确认完成必须同时满足：

1. 当前用户的已注册包版本达到或超过目标版本。
2. Windows 包状态为 `Ok`。

版本已变化但仍为 `Servicing`，或者新版仅处于暂存状态，均不算完成。守护器定期读取本机状态，“核对更新结果”也只查询结果，不反复提交安装。界面显示版本、等待原因、下次自动检查及最近确认更新时间。

## 等待停滞与“完成已下载更新”

待生效超过十分钟时显示注册停滞；检测到系统待重启标记时给出保存工作并重启 Windows 的提示。该标记是排查依据，不是唯一故障原因，也不保证重启一定解决问题。

“完成已下载更新”是显式安排一次原位安装尝试：

1. 先核对 Windows 是否已完成目标版本，已完成则无需再安装。
2. 如果需要重启，记录当前系统启动时间，真正重启后才继续；重开客户端或守护器不能代替重启 Windows。
3. 等待当前包状态正常、客户端及相关 CLI 退出、守护检查通过。
4. 重新验证已下载包的签名和身份，再尝试一次不带延后注册参数的原位部署。

部署前先持久记录这次安排已消费。若守护器在安装期间崩溃、结果未知、Windows 拒绝或仍报告占用，停止自动安装重试，保留错误和目标供手动排查。只有在提交部署 API 之前发现程序重新运行、确认尚未提交安装时，才继续等待退出。

关闭自动更新会取消守护器自己的后续尝试，但不能撤回 Windows 已接收的更新，仍可核对结果。网络检查或下载失败保留下一周检查计划；签名、部署和包健康异常需要手动处理，不进行破坏性回退。

## 常见状态

| 状态或现象 | 含义与处理 |
| --- | --- |
| 等待客户端 / CLI 退出 | 保存工作后正常退出列出的程序，保持守护器运行。 |
| 等待守护检查通过 | 先处理代理或出口配置，再继续更新。 |
| Windows 已接收，等待生效 | 目标尚未确认注册完成，可用“核对更新结果”查询。 |
| 注册停滞 / 系统待重启 | 按界面安排一次完成操作；需要重启时先保存工作，由用户重启。 |
| `0x80073D02` | Windows 仍认为包被占用；不要反复提交或强制结束无关任务。 |
| `Servicing` 或注册失败 | Windows 包状态不健康，需结合系统部署日志排查；重启后仍异常时不能直接视作最新版或继续自动安装。 |
| 网络检查通过但 Claude 未打开 | 网络检查结果和应用启动结果分别显示。包状态异常或无法提交启动请求时，主界面保留具体原因；启动请求已提交不代表窗口已打开。 |

更新器不会自动卸载、重置、修复、清理登录档案、修改系统包数据库或重启电脑。应用包恢复与登录状态仍需在真实环境验收，模拟测试通过不等于特定电脑已完成升级。

本地状态保存在 `%APPDATA%\ClaudeGuard\claude-update.json` 和 `codex-update.json`。`--claude-update-status` / `--codex-update-status` 只输出这些状态的快照，不联网检查，也不提交安装。使用运行中的守护器界面配置和手动操作。
